## P0：开始整页重构前必须明确

### 1. 字号、触控与圆角的规格冲突

实测原型正文为 14 px，模型胶囊文字为 11 px、控件高 33 px；附件按钮 36×36，发送按钮 38×38；审批按钮高 46、圆角 14。规范则要求 Body 16、Label 14、默认按钮高 48、圆角 16。现有 CSS 未给这些小按钮独立扩大命中区。数字见审查 JSON。

开发采用以下统一目标，不照搬原型小字号：

| 项目 | 重构目标 |
|---|---|
| 会话正文 / 编辑内容 | 16，跟随平台文本缩放；默认行高参考 26 |
| 按钮 / 模型选择文字 | 14；次要信息最小 12 |
| 普通动作按钮 | 最小高 48，圆角 16；大字体时允许增长 |
| 图标按钮 | 视觉图标 20–24；实际命中框 iOS ≥44、Android ≥48；相邻命中框不重叠 |
| 紧凑模型胶囊 | 视觉高可为 32–36；独立布局槽保证上述命中框；端头半径为视觉高度一半 |
| 主机 / 任务卡片 | 圆角 22；圆角不要与卡片高度同比放大 |
| 输入容器 | 圆角 24；多行增长时保留固定圆角 |
| 用户消息 | 左上 / 右上 / 右下 / 左下 = 19 / 19 / 5 / 19；不能统一成四角 19 |
| 详情 / 确认 / 结果卡 | 16 / 20 / 18；如抽为同种组件，再统一命名和使用规则 |
| 底部面板 | 上角 30、下角 0；实际安全区交给平台 |

`ROUNDING-v1.1.md` 的 14 是旧页面稿的按钮数值；生产实现以本表 16 为准。不要增加任意大小的全局圆角开关来替代组件规则。间距应随字号重新排版，不能为了维持旧截图高度挤压正文。

### 2. 输入框应覆盖真实执行过程

现有代码包含停止执行、排队 follow-up、引导当前任务、计划进度、附件、模型 / 推理强度与权限选择。新稿只演示了基础发送框。

- 空闲：无有效输入时发送不可用；输入文字或受支持附件后启用。
- 执行中：保留显式停止入口；追加输入根据已有能力显示“发送 / 排队 / 引导”的准确动作，不能假装总是启动新任务。
- 排队：展示数量与内容摘要，保留现有编辑、取消或引导能力；操作成功由共享状态确认。
- 停止提交中：禁止重复停止，显示“正在停止”；远端仍运行时不能提前显示已完成。
- 断线：保留输入与附件，说明状态待同步；是否允许排队遵循现有能力，不新增离线执行假象。
- 失败：保留草稿、选择范围及附件，提供可见重试；成功清空输入的时机沿用权威确认语义。
- 键盘：输入区与主要动作跟随键盘安全区；短屏下正文可滚动，输入区不能被屏幕底部或键盘覆盖。
- 模型选择：区分“搭档 / 运行时”（Codex、Claude Code）与“模型 / 推理强度”；依据当前服务端能力决定会话内是否可切换，不支持时解释原因并引导新建任务。

原型已确认的导航缺陷：从会话点击搭档选择，再选择 Claude Code，会打开“开始一个新想法”而不是返回会话。回复草稿仍在原会话，但新建框为空。这是演示缺陷，不是期望行为。选择器必须记录来源；取消恢复来源与焦点；确认后仅更新受支持的设置并返回来源。

### 3. 审批不止一种命令确认卡

Android `ApprovalOverlay.kt` 中已存在 COMMAND、FILE_CHANGE、PERMISSIONS、MCP_ELICITATION，以及 DECLINE / ACCEPT_FOR_SESSION / ACCEPT。不能因画稿只画两个按钮，就移除现有能力或自行替换请求含义。

- 默认优先展示“拒绝 / 允许一次”，明确这是决策；避免“暂不允许”与关闭面板混为一谈。
- 若后端支持会话范围授权，保留明确的次级入口和范围说明；不默认选中，不自动扩大授权。
- 文件审批展示路径、变更摘要与查看差异入口；权限审批展示具体范围；工具询问使用其真实字段与校验。
- 长命令或多文件内容进入可滚动 / 展开的内容区域，动作区保持可达。复制操作不触发执行。
- Pending / Submitting / Allowed / Denied / Expired / SubmitFailed / ResolvedElsewhere 都有展示；请求标识与真实决策传给现有共享实现。
- 多个请求显示待处理数量并逐个处理。关闭展示层不等于拒绝；已过期或其他设备处理的请求不能继续提交。

### 4. 导航改版不能丢失已有功能

“任务 / 项目 / 主机”是新信息架构，需要显式接入已有页面。首页需要一个可发现的设置入口。以下现有能力必须在迁移清单中有去处：

| 能力 | 新界面建议位置 | 必须保留的行为 |
|---|---|---|
| 任务搜索、固定、隐藏、删除、派生、快捷回复、停止 | 任务页、卡片菜单、搜索 | 保留列表位置和原有作用范围；长按不是唯一入口 |
| 主机过滤与任务归属 | 任务页筛选、项目详情 | 明确当前主机 / 项目；计数与列表同范围 |
| 项目与工作目录 | 项目页、项目选择 / 目录选择面板 | 显示主机归属；项目与主机切换后重新验证目录兼容性，保留文字草稿 |
| 主机发现、扫码、手动连接、SSH、重连、重命名、断开 | 主机页及详情菜单 | 保留各平台已有连接方式、信任和权限流程 |
| 外观、账号、连接配置、会话展示偏好 | 设置 | 保留用户已选主题、字体、壁纸等偏好，不静默重置 |
| Saved Apps、挂载目录、实验终端、宠物等 | 已有页面与上下文入口，按原 feature flag | 本次重构不隐式删功能，也不启用原本关闭的实验特性 |
| 通知进入任务 | 路由至对应主机和会话 | 冷启动、后台恢复、目标不可用都有处理；原通知抑制行为保持 |

手机三入口可以重构，已有 iPad 分栏不能被统一手机壳替换。原生返回手势和 Android 返回栈必须保持。Android 根路由目前没有独立“项目”页面，不能只替换底栏外观而遗漏实际导航。

## P1：视觉与内容补齐

| 缺口 | 完善方向 | 验收点 |
|---|---|---|
| 首页装饰区较大 | 有活跃任务时缩短口号区；待确认优先可见；首次空态再使用完整品牌文案 | 短屏进入后可直接看到最需处理的任务；多个运行任务不能只显示一张示例卡 |
| 空态与失败态缺图 | 补无主机、无任务、无项目、搜索无结果、加载失败、主机离线 | 每个状态给一个准确下一步，不能全部复用“重试” |
| 内容展示覆盖不足 | 补长 Markdown、代码、diff、图片、工具卡、思考区、子任务、计划进度 | 不丢复制 / 折叠 / 预览；长代码仅代码区横向滚动，正文不横滚 |
| 流式更新与阅读位置 | 用户在底部时跟随；上翻时保持锚点并显示“回到最新” | 不因流式追加或工具卡高度变化把用户拖回底部 |
| 长内容布局 | 80 字任务标题、长英文单词、深层目录、长模型名、三位数计数 | 不缩小正文救布局；标题至多两行，必要命令和错误可完整展开 |
| 深色覆盖不足 | 目前只有独立深色首页稿；补会话、审批、输入、主机和弹层 | 语义颜色逐项映射；深色卡片层级、错误及禁用状态清楚 |
| 嵌套圆角 | 按钮、卡片和输入容器分层使用既定 token | 胶囊端头不拉成椭圆；面板底角、安全区、裁剪保持一致 |
| 视觉边界与无障碍 | 颜色报告只是指定组合检测；实际控件还要看识别边界、字号与命中区 | 对比度报告不能当成整页无障碍通过；VoiceOver / TalkBack 按逻辑顺序读 |
| 文案与国际化 | 中文少用装饰性全大写英文；主机 / 项目 / 搭档 / 模型术语固定 | 英文扩展后按钮可换行；时间、单位本地化；不翻译存储哨兵 This Device |
| 模态面板 | 来源、关闭、取消、保存语义统一；系统输入法和焦点按平台处理 | 关闭恢复焦点；大字体 / 横屏使用足够高的 sheet 或全屏页 |

优先补充的高保真状态：① 无主机首页；② 多任务与待确认首页；③ 执行中输入＋排队；④ 键盘升起与长文本；⑤ 文件 / 权限审批＋提交失败；⑥ 断线后重连；⑦ 长内容会话；⑧ 设置与连接编辑。每组至少覆盖浅 / 深色；长内容另做 320 宽和大字体版本。这些尚未补画，不应在开发完成报告里写成现成设计。

| 富内容 | `MessageBubbleView.swift`、`ToolCallCardView.swift`、`CodeBlockView.swift`、`DiffRendering.swift` | `ui/conversation/StreamingMarkdownView.kt`、`DiffRendering.kt`、`SubagentCard.kt` 等 |
| 主机 / 配对 | `DiscoveryView.swift`、`AlleycatAddServerSheet.swift`、`SSHLoginSheet.swift` | `ui/discovery/DiscoveryScreen.kt`、`AlleycatAddServerSheet.kt` 与现有连接编辑流程 |
| 主题 | `Models/ThemeDefinition.swift`、现有 ThemeManager 与 Resources/Themes | `ui/AgentBuddyTheme.kt`、`AgentBuddyThemeManager.kt` 与共享打包主题 |

iOS 相对前缀：`apps/ios/Sources/AgentBuddy/`；Android 相对前缀：`apps/android/app/src/main/java/com/akashark/agentbuddy/android/`。表是入口索引，不是完整待改文件列表，开发需追踪真实调用关系。

共享会话、审批、状态、发现合并、语音交接继续由 `shared/rust-bridge/codex-mobile-client/` 的 Rust / AppStore / AppClient 管理。Swift / Kotlin 只改 UI 与平台展示。不得在本次重构里复制 reducer、解析 wire strings 或伪造任务状态。需要共享新行为时按仓库 AGENTS.md 放回 Rust，再同时验证两端。

不建议一次重写全部复杂渲染器。先替换主题和外层组件，再复用现有 Markdown、diff、终端、语音、WebView 和共享状态接口。Icon / splash / 首页品牌图分别核对，不能只换商店图标；采用本地 Lucide 资产时保留许可证。

## 推荐实施顺序

1. 建功能保留清单，记录当前截图、平台差异、任务状态与入口。确认当前工作区的其他改动，不混入本次 UI 工作。
2. 建语义颜色、字体、间距、圆角、按钮与状态组件。Mint 默认主题策略：新安装可采用 Mint；已有明确主题偏好保留。现有 JSON 不足以表达全部语义时补兼容映射。
3. 完成一条真实纵向流程：任务首页 → 会话 → 输入 / 执行中 → 审批 → 结果。iOS / Android 同步验证，先验证状态完整性，再扩展页面。
4. 扩展项目 / 主机 / 搜索 / 设置和配对流程；保留已有高级功能及 feature flags。
5. 补长内容、空 / 错误 / 断线、大字体、深色与宽屏；生成实际设备截图与视觉对照。
6. 最后替换商店展示稿中的概念 UI，并重新导出。尚未实现的界面不能直接充当真实商店截图。

可以从第 1–2 步开始开发；整页最终验收前必须完成 P0 行为映射和相关 P1 状态。Figma 原生组件库会提升复用，但不应阻止先建立两端代码组件。不要把当前 SVG 分组当成可直接转换的 SwiftUI / Compose 布局树。

## 验收场景

| 场景 | 必须观察到的结果 |
|---|---|
| 320 / 390 / 430 逻辑宽度，标准 / 大字体；另测 iPad 与 Android 宽屏 | 无文字重叠、截断关键动作或全页横滚；触控框互不重叠 |
| 键盘、多行草稿、附件、切模型后取消 / 确认 | 草稿不丢、回原上下文；动作可达；不误新建任务 |
| 执行中追加、排队、停止 | 真实状态与队列一致；不重复启动 / 停止；支持现有引导能力 |
| 长命令、多文件审批、权限、工具询问、并发请求 | 参数可读；按钮可达；重复点击只提交一次；过期不可批准 |
| 刷新、上翻长会话、流式输出、工具卡展开 | 阅读锚点稳定；能回到最新；历史不闪空 |
| 首次使用、空搜索、离线、断线恢复、提交失败 | 提供明确下一步；不丢输入；不把连接失败等同于任务失败 |
| 后台恢复与通知进入任务 | 返回准确会话；保留正常导航与通知抑制规则 |
| 浅 / 深色，VoiceOver / TalkBack，减少动态效果 | 状态有文字与图标；焦点顺序正确；装饰动效可关闭 |
| 已有主题 / 字体 / 壁纸偏好、实验开关、Saved Apps 等 | 原配置保留，已有功能可发现且可用 |

开发验证使用仓库 fast lanes：`make ios-sim-fast`、`make android-emulator-fast`。按实际变更运行相关测试，更新 `apps/android/docs/qa-matrix.md` 的对应覆盖，并提供两端实际截图与关键交互证据。只改设计文档不运行全量原生构建；当前审查未宣称上述原生场景通过。

## 可复制给开发会话的任务

请先阅读 `AGENTS.md` 与 `docs/design/mobile-ui-rebuild-handoff.md`，以 Figma v1.1 的 Mint 视觉方向和交接文档中的生产尺寸、行为约束，完成 AgentBuddy iOS / Android 整体 UI 重构。素材在 `artifacts/design/agentbuddy-ui-v1/`。先核实素材是否可读；缺少素材时使用交接中的 Figma 链接，不以缺失原稿为由编造已验证结果。先建现有功能保留清单和语义组件，再打通任务首页到会话、输入、审批、结果的真实流程，随后覆盖项目、主机、设置、配对与边界状态。保留现有功能、主题偏好和 feature flags；共享业务仍由 Rust 管理，Swift / Kotlin 保持 UI 投影。不要照搬原型切搭档误回新任务、模拟配对 / 语音、过小触控区等演示缺陷。按文档的双端验收场景完成验证并交付实际截图、测试结果和未解决事项；不要仅换色或删掉复杂功能来完成重构。
